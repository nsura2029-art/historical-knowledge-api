## Gotchas hit

### Schema mismatches
- `people_ingest.py` had wrong `person` table columns: `primary_profession` instead of `primary_profession_id`, plus extra non-existent columns (`nationality`, `birth_year`, `death_year`).
  - Fixed by replacing with correct schema (30 columns matching the current person table).
- `us_places_seed.py` had wrong `place` table columns: `country` instead of `country_code`, plus extra `state`, `population`, `significance` (none exist).
  - Fixed: only insert (id, place_type, country_code, valid_from, wikidata_qid).

### FK constraint with INSERT OR IGNORE
- `INSERT OR IGNORE` does NOT bypass FK violation checks in SQLite.
- `person_place_relation` and `entity_relation` both had FK issues when linking to non-existent entities.
- Fix: wrap each row with a subquery that only inserts if both subject and object exist:
  ```sql
  INSERT INTO person_place_relation (cols) SELECT 'val1', 'val2' ... 
    WHERE EXISTS (SELECT 1 FROM entity WHERE id='val1') 
      AND EXISTS (SELECT 1 FROM entity WHERE id='val2');
  ```

### Slug uniqueness
- Charles Schwab person slug collides with Charles Schwab Corporation org slug (F500).
- Skip strategy: drop person 184 from migration; F500 org already has the slug.

### wrangler d1 execute limitations
- BEGIN TRANSACTION not allowed via wrangler — must use JS storage API instead.
- INSERT OR IGNORE doesn't bypass FK — must use subquery pattern.
- `wrangler d1 execute --file=...` with SELECT doesn't return rows in JSON output.
- Long IN clauses via `--command` may not work — use --file= with the static SQL (chunks of 30 for `IN (...)` to stay under limits).

### Batch upload of migrations
- Migration 0034 (200 people × 4 statements each) failed on person 184 due to FK.
- Workaround: split into per-person batches and apply individually, skipping the one with slug collision.
- Each batch typically 24 lines (entity + person + 4 content_sections) and takes <1 sec.
